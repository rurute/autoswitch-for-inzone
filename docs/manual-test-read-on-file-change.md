## Task 1: 前提の計測（2026-10-18）

1. Hub が `ActionLog.log` を開いたまま書いているとき、`FileSystemWatcher` の通知がすぐ届くか
2. 接続・切断の行が書かれてから、truncate されるまでの時間

### 分担

- **作業環境**: 計測ツールの起動・停止、要約と CSV の読み取り、判定と記録。

### 手順

ツールは、通知を受けたとき・1 秒ごと・10 ms ごと（長さだけ）の 3 通りで `ActionLog.log` を読み、ms 単位の時刻を付けて CSV に記録する（spec §7「測り方」）。起動するとまずファイルを末尾まで読んで基準線にし、そこより前の行は数えない。止めるときは標準入力に Enter を送る（ここでは FIFO 経由）。

```bash
inzone_repo_win=$(wslpath -w "$PWD")
dotnet.exe run --project "$inzone_repo_win\\tools\\LogTimingProbe\\LogTimingProbe.csproj" -- \
  'C:\Users\<user>\AppData\Roaming\Sony\INZONE Hub\ActionLog.log' '<CSV の出力先>' <> <FIFO>
```

- 21:53:24.917（`start_ms`）に計測を始めた。基準線より前の行（数えない）は 68 行
- 作者が 21:53:25〜21:56:20 の間に Buds を出し入れした（作者の申告は「5〜6 往復」）
- 21:56:20.417 に止めた。計測時間は 175.5 秒

CSV（約 18,000 行）は記録用に作業環境に残し、コミットしていない。

### 観測・上限・仮説の区別

- **観測**: 通知は接続・切断の 15 行すべてで届いた。最初に読んだのはどれも通知で、遅れの上限は 14 ms 以内だった。truncate は 2 回起きた。どちらも、23004 の行を通知で読んだ直後（読んでから約 1 ms 後）に、0 バイトになったのを見た
- **上限**: その 23004 の行が書かれてから空にされるまでは、11 ms 以下と 13〜14 ms 以下（`timeStamp` から縮んだのを見た時刻まで）。実際の時間はこれより短いことがある
- **仮説（確かめていない）**: 2 回とも、縮む前の長さが約 100KB を超えた直後に空になっている。このことから、「Hub は約 100KB を超えたら、書いてから 10〜15 ms のうちに空にする」という仮説が立つ。ただし、閾値の値も条件も確かめていない（1 回目は 104,470 バイトでは空にならず、105,559 バイトで空になった）
- **未観測**: 接続・切断の行が、truncate の直前の行（境目）になる場面は観測していない。そうなったときに、書いてから空にするまでの窓がどれだけ短いかは不確かである。上の 23004 の行と同じなら 10〜15 ms 程度、もっと短いかもしれない
- spec §7 の「下限の最短 3693 ms」は、truncate の何秒も前に書かれた接続の行から測った値である。接続・切断の行が境目になる場面での窓の長さは表していない

### 判定（spec §7 の表）

| 結果 | 当てはまるか |
|---|---|
| 通知が毎回届き、書き込みから通知までがすべて 50 ms 以内 | 当てはまる（届かなかった 0 行、最大 14 ms）→ 進む |
| 下限の最短が 300 ms 以上 | 当てはまる（3693 ms）→ 最小間隔は初期値 100 ms のまま |
| 上限の最短が 50 ms 未満 | 接続・切断の行では当てはまらない（3701 ms） |
| 切断・接続が 3 回ずつに満たない | 当てはまらない（接続 10・切断 5） |

表のとおりに当てはめると「進む」で、最小間隔は 100 ms のままになる。

ただし上の「未観測」のとおり、接続・切断の行が境目になる場合の窓は 10〜15 ms 程度かそれより短いかもしれない。その場合、直前の `Tick` から 100 ms たっていなければ、行を読む前に空にされうる。この不確実性を作者に示した。

- 示した選択肢 1: 「Proceed at 100 ms with explicit acceptance of this uncertainty.」（最小間隔 100 ms のまま進め、接続・切断の行が truncate の境目になる場合の、観測していない短い窓の不確実性を受け入れる）
- 作者の回答（原文）: 「1 で進めて」（2026-10-18 22:02）

### 決めた最小間隔

**100 ms（初期値のまま）**。理由は 2 つ。

1. spec §7 の表で、下限の最短（3693 ms）が 300 ms 以上だった
2. 接続・切断の行が境目になる場合の不確実性は、作者が受け入れて 100 ms のまま進めると決めた（上の「1 で進めて」）
