## 1. 目的

INZONE Hub が `ActionLog.log` に書いた接続・切断の行を、**Hub がログを送って中身を空にする前に**読めるようにする。

いまは 1 秒ごとにファイルを読んでいる（`pollIntervalSeconds` の既定値 1）。Hub はログをサーバーへ送ったあと中身を空にする（truncate）。2026-10-18 21:16 ごろに切断を取りこぼした。消えた行そのものは残っていないが、前後のログから、Hub が切断の行を書いてから空にするまでが 0.65 秒未満で、次の読み取りの前に行が消えたと推定している（Issue rurute/inzone-auto-switch#21 に経緯と根拠）。

作者が取りこぼしに気づいたのはこれが初めてで、ふだんは問題なく動いている（気づいていない取りこぼしが無いとは言い切れない）。本書は、まれに起きる競合を**さらに起きにくくする**ための修正で、仕組みを作り直すものではない。

## 2. 目標・やらないこと

### 目標

- ファイルが書き換わったという Windows の通知を受けたら、1 秒待たずにすぐ読む
- 通知が来ない・通知の仕組みが使えないときも、今までどおり 1 秒ごとに読んで動き続ける

### やらないこと

- **100% 防ぐことは目指さない。** Hub が書いてから空にするまでの間に読めなければ、行は消える。そこは割り切る
- **取りこぼしたあとの穴埋めはしない。** 空にされたあとの行（未接続画面の表示記録、バッテリーの `Disconnect` など）から切断を推測することはしない。Hub の書き方が変わると壊れやすいため（作者と合意）
- **設定項目は増やさない。** 設定画面にも `config.json` にも項目を足さない（実装者側の判断として合意）
- 切り替えの判断（状態が変わったときだけ切り替える、`logId` で重複を除く、起動時同期）は変えない

### 失敗とみなすこと

- 通知の仕組みが原因で、常駐が止まる・トレイが出ない・今までより取りこぼしが増える
- Hub が行を書くたびに切り替えが二重に起きる、または CPU を目に見えて使い続ける

## 3. 既存の仕組みとの関係

- `MonitorLoop.Run` は「待つ → `engine.Tick` → 待つ…」を繰り返し、待つ長さは `engine.NextDelaySeconds`（通常 `pollIntervalSeconds`、Hub 不在時は `idlePollIntervalSeconds`、読み取り失敗時は倍々で最大 60 秒）で決まる。**この待機を、通知が来たら途中で打ち切れるようにする**のが本書の変更の中心である
- `Tick` の中身（読み取り、truncate・再生成の検知、イベントの解析と切り替え）は変えない
- `ActionLogReader` は何度呼ばれても正しく動く（途中行は持ち越し、追記が無ければ何も返さない）。よって読む回数が増えても結果は変わらない
- 終了の契約（取り消しが効くのは待機だけ、取り消しのあとの音声操作は多くとも 1 回）は変えない

## 4. 動作

### 通知を受ける

- `actionLogPath` のあるフォルダを見張り、そのファイル名についての変更（書き込み・サイズ変更・作成・削除・名前の変更）を受ける。Windows の `FileSystemWatcher` を使う
- 通知を受けたら、監視ループの待機を打ち切って、すぐ次の `Tick` を行う
- 通知は短い間に何回も来うる（Hub は接続のときなどに数十行を数秒のうちにまとめて書く。2026-10-18 21:17:35〜42 の 7 秒で 32 行）。待機中に何回来ても、打ち切りは 1 回分にまとめる。`Tick` の最中に来た通知は、`Tick` のあとの待機をすぐ打ち切らせる（取りこぼさないため）

### 読む回数の上限

- 通知で打ち切った直後の `Tick` から次の `Tick` までは、少なくとも**最小間隔**を空ける。Hub がまとめて書く間に読み取りが続きすぎないようにするため。最小間隔の初期値は **100 ms** とし（実装者の判断）、§7 の実測の結果で下げることがある。値はコード上の 1 つの定数に置き、設定項目にはしない
- 読み取り失敗が続いて待機が延びているとき（倍々の待機）や、Hub 不在で `idlePollIntervalSeconds` 待っているときも、通知が来たら打ち切ってよい。通知が来たということはファイルが存在して書き換わったので、読みに行く価値がある

### 通知の仕組みが使えないとき

- 起動時にフォルダが無い（Hub を入れていない・初回起動前）などで見張りを始められないときは、ログに 1 回だけ記録し、今までどおり時間だけで読む。見張りの開始は、`Tick` のたびに（またはそれより粗い間隔で）やり直す。始められたらログに 1 回記録する
- 見張りの途中でエラー（通知のあふれ、フォルダの削除など）が起きたら、ログに記録し、見張りを作り直す。作り直せない間は時間だけで読む
- どの場合も、通知まわりの例外で監視ループや常駐を止めない

### ログ

| 場面 | レベル | 文言（案） |
|---|---|---|
| 見張りを始めた | Info | `ActionLog.log の変更通知を受け取ります。` |
| 見張りを始められない | Warn | `ActionLog.log の変更通知を受け取れません。1 秒ごとの読み取りだけで監視します: {詳細}` |
| 見張りのエラー | Warn | `ActionLog.log の変更通知でエラーが発生しました。見張りを作り直します: {詳細}` |

同じ文言が続くときは既存の `BoundedLog` などの抑制に従う。通知 1 回ごとのログは出さない（Debug でも出さない。短い間に何回も来るため）。

## 5. 構成（実装者に任せる部分を含む）

- Core には、待機を外から打ち切れる仕組み（例: `IWaiter` に「起こす」入口を足す、または待機に使う `WaitHandle` を差し替えられるようにする）だけを置き、実機なしでテストできるようにする
- `FileSystemWatcher` の生成・作り直し・破棄は App 側（`MonitorRunner` 付近）に置くか、Core に薄い包みを置くかは実装者に任せる。いずれの場合も、終了時（`MonitorRunner.Dispose`）に見張りを止めて破棄する
- 最小間隔をどこで守るか（ループ側か待機側か）は実装者に任せる

## 6. テスト

- 単体テスト（Core）
  - 待機中に起こすと、待機時間を待たずに `Tick` が行われる
  - 待機中に何回起こしても、`Tick` は 1 回だけ行われる
  - `Tick` の最中に起こすと、その次の待機がすぐ終わる
  - 起こしたあとの `Tick` と次の `Tick` の間が最小間隔（§4 の定数。§7 で決めた値）を下回らない
  - 取り消しは今までどおり待機を終わらせ、起こしても取り消しのあとに `Tick` は行われない
  - 起こさなければ、今までどおり `NextDelaySeconds` だけ待つ（既存テストがそのまま通る）
- 見張りの単体テスト（実ファイルを使ってよい）: 一時フォルダのファイルに追記すると起こされる、フォルダが無いと見張りを始められずに例外を出さない
- 既存の `ActionLogReader`・`AutoSwitchEngine`・`MonitorLoop` のテストはすべて通る

## 7. 実機での確認

計画の最初に、実装の前提を実測する（使い捨ての計測でよい）。

1. Hub が `ActionLog.log` を開いたまま書いているときに、`FileSystemWatcher` の通知が書き込みのたびにすぐ届くか（NTFS はファイルを開いたままの書き込みでサイズや更新日時の反映を遅らせることがあるため、届かない・遅れる可能性がある）
2. 接続・切断の行が書かれてから truncate されるまでの時間

#### 測り方

計測ツールは次の 3 つを、すべて時刻（ローカル時刻、ms）付きで記録する。

- `FileSystemWatcher` の通知を受けるたびに、ファイルを読み、新しく増えた行とファイルの長さを記録する
- 通知とは別に、1 秒ごとにもファイルを読み、新しく増えた行を記録する
- 通知とは別に、10 ms ごとにファイルの長さだけを調べて記録する（行は読まない。空にした時刻を細かく挟むため）

ここから次のように求める。

- **書いた時刻**の下限は、Hub が各行に書く `timeStamp`（ms）とする。Hub とツールは同じ PC の時計を使うので比べられる。Hub は `timeStamp` を付けてから書き込むので、実際の書き込みはこれ以後である。よって「通知で行を読んだ時刻 − `timeStamp`」は、書き込みから通知までの時間の**上限**になる。50 ms の判定はこの上限で行う（上限が 50 ms 以内なら、実際も 50 ms 以内）
- **通知が届かなかった**とは、ある行を最初に読んだのが通知ではなく 1 秒ごとの読み取りだった場合とする
- **空にした時刻**は、「縮む前の長さを最後に見た時刻」（以後 A）と「縮んだ長さを最初に見た時刻」（以後 B）の間にある。10 ms ごとの記録と通知での記録の両方を使う
- **書いてから空にするまでの時間**は、接続・切断の行ごとに 2 つの値で挟む
  - 下限 = A − その行を最初に読んだ時刻（実際の書き込みは読んだ時刻以前、空にしたのは A 以後なので、実際の時間はこれ以上）
  - 上限 = B − その行の `timeStamp`（実際の時間はこれ以下）
- truncate の前に接続・切断の行を読めなかった場合は、その回は「通知が間に合わなかった」として扱う
- Buds の出し入れは 3 往復以上（切断・接続それぞれ 3 回以上）行う。truncate は毎回起きるとは限らないので、書いてから空にするまでの時間は、truncate が起きた回だけで見る。truncate が 1 回も起きなかった場合は、この時間についての判定はせず、最小間隔は初期値のままとする

「長い」と言うときは下限で、「短い」と言うときは上限で判定する。下の表の「最短」は、truncate が起きた回の中で最も小さい値を指す。

#### 進むか止まるか（作者と合意）

| 結果 | 扱い |
|---|---|
| 通知が毎回届き、書き込みから通知までがすべて 50 ms 以内 | 進む |
| 1 回でも通知が届かない、または 50 ms を超えて遅れる | 止まって作者に相談し、方針を見直す（例: 読み取り間隔を 100〜200 ms に縮める） |
| 書いてから空にするまでの下限の最短が 300 ms 以上 | 最小間隔は初期値（100 ms）のままで進む |
| 下限の最短が 50 ms 以上 300 ms 未満 | 最小間隔（初期値 100 ms）を、下限の最短の 3 分の 1 以下に下げて進む。下げた値と理由を計画と手動確認記録に残す |
| 上限の最短が 50 ms 未満 | 通知が来てもまず間に合わないので、止まって作者に相談する |
| 下限の最短が 50 ms 未満で、上限の最短は 50 ms 以上（どちらとも言えない） | 判定できないものとして扱い、進まない。測り直すか、作者に相談する |
| 切断・接続が 3 回ずつに満たない、または記録が欠けて上の判定ができない | 進まない。測り直すか、作者に相談する |

実装後は、Buds の出し入れを何回か行い、毎回 `状態遷移を検知しました` が出て切り替わること、truncate を挟んでも二重に切り替わらないことを確かめ、手動確認記録（`docs/manual-test-read-on-file-change.md`）に残す。
