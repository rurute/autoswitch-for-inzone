# INZONE Hub なしで接続・切断を判定する（ドングルへの直接の問い合わせ、Issue rurute/inzone-auto-switch#23）

## 目的

今の AutoSwitch for INZONE は、INZONE Hub が書く `ActionLog.log` を読んで、Buds の接続・切断を判定している。そのため Hub を常駐させておく必要がある。

これを、Buds の USB ドングルに直接問い合わせて判定する形に置き換え、**Hub を常駐させなくても切り替えられる**ようにする。

作者の最終的な目標は「Hub の機能のうち、使うものを inzone-auto-switch に持たせる」こと。ただし、作者は普段 Hub の機能をほとんど使っていない。そこで今回は接続・切断の判定だけを置き換える。Hub はアンインストールせず、ファームウェア更新などで必要なときに手で起動する。

## ゴール / 非ゴール / アンチゴール

- ゴール: Hub が起動していなくても、Buds をケースから出す・ケースに戻してふたを閉じるに合わせて、今と同じように既定の再生デバイス（と、設定していれば録音デバイス）が切り替わる。
- ゴール: Hub が起動していても同じように動く（Hub の常駐をやめる前と後のどちらでも使える）。
- ゴール: 切り替えまでの遅れは、取り出す側で 1〜2 秒、ふたを閉じる側で 3 秒程度（返答が止まるまで約 1 秒 + 1000ms の時間切れ 2 回）。閉じる側の 3 秒は HUMAN が許容した（2026-11-25）。待ち時間を縮めると、返答に 0.4 秒ほどかかる場面で切断と取り違えるおそれがあるため。
- ゴール: Buds のドングル（`054c:0ec2`）だけを見るので、Buds 以外の INZONE 機器には反応しない（Issue rurute/inzone-auto-switch#19 が解消する）。
- 非ゴール: バッテリー残量の表示（battery-hub で見ている）、イコライザーなど Hub のほかの機能。
- 非ゴール: Bluetooth で Buds をつないだときの判定。今回はドングル経由だけ。
- 非ゴール: 旧 PowerShell 版（`src/INZONE-AutoSwitch.ps1`、`src/modules/`）。手を入れない。
- アンチゴール: Hub の動作を邪魔すること（Hub の表示や設定がおかしくなる）。
- アンチゴール: 片耳だけケースに戻した（ふたは開いたまま）ときに、スピーカーへ切り替わってしまうこと。今の Hub ログでの動きと同じく、接続中のままにする。

## 確認用プログラムで分かったこと（2026-11-25、作者の環境）

使い捨ての PowerShell（C# を埋め込んだもの）で、ドングルの COL03 に 2 秒おきにバッテリーを問い合わせ、15 分間記録した。問い合わせと返答の形は battery-hub の `src/main/hid/drivers/inzone.js`（fork Issue #3 で実機確認済み）と同じ。

| 操作（Hub は終了した状態） | 返答 |
|---|---|
| 耳に着けている | 返る。左 100 / 右 100 |
| 片耳だけケースへ（ふたは開けたまま） | 返る。左 報告なし（`0xFF`）/ 右 100 |
| ふたを閉じる | 約 1 秒後から返らない（1000ms 待って時間切れ） |
| ふたを開けて取り出す | 約 1 秒で返るようになる |
| 閉じる・取り出すの 2 回目 | 1 回目と同じ |

- Hub が起動していても、終了していても、問い合わせには同じように返った。Hub を終了してから起動し直しても変わらなかった。
- **状態が変わったときに、ドングルが自分から知らせ（type `0xA0` のフレーム）を送ってくる。** Hub が起動していないときにも届いた。ふたを閉じる・開ける・耳から出し入れするたびに、event `0x01` と `0x41` のフレームが届いた。event `0x01` の `[13]` `[14]` は左右それぞれの接続を表しているように見える（両耳 `01 01`、片耳 `00 01`、なし `00 00`）。ただし数回分からの推測で、確かではない。Hub が起動しているときに知らせが届くかは確かめていない（その時間に状態を変えていない）。
- 読み取り用と書き込み用に、同じ COL03 のハンドルを 2 つ開いた（読み取りは別スレッドで待ち続ける）。

記録したフレームの例（テストの入力に使う）:

```
Hub の返答（TID=1、左 100 / 右 100 / ケース 100）: 021204ff0f0096c3140410010000640064ff64ad
知らせ event 0x01（片耳）: 020e04ff0b0096c31201a0000000010d
知らせ event 0x01（なし）: 020e04ff0b0096c31201a0000000000c
知らせ event 0x41:         021004ff0d0096c31441a001000014ff0062
```

## 検討した案

HUMAN が選んだ: **案 2**。

1. 問い合わせだけで判定する: 数秒おきに問い合わせ、返答がなければ切断。確かめた動きだけに頼るので確実だが、切り替えが問い合わせの間隔ぶん（最大 4 秒ほど）遅れる。
2. **知らせを合図にして、すぐ問い合わせる（採用）**: ドングルからフレームが届いたら待たずに問い合わせ、その返答で判定する。知らせの中身は読まず、「何か変わったかもしれない」という合図にだけ使う。知らせが来ない場合に備えて、一定の間隔での問い合わせも続ける。今の「ログが変わったら起きてすぐ読む」（Issue rurute/inzone-auto-switch#21）と同じ形で、`WakeableWaiter` をそのまま使える。推測した中身の読み方に頼らずに速く切り替えられる。
3. （外した）知らせの中身（event `0x01` の左右の接続）で判定する: 問い合わせが要らず最も速いが、読み方が推測なので外した。

Hub のログとの関係（HUMAN が選んだ: 案 A）:

- **ログを読む部分は削除し、ドングルへの問い合わせに置き換える（採用）**。必要になれば git の履歴から戻せる。
- （外した）両方を残して設定で選ぶ: 仕組みが 2 つになり、テストも設定画面も膨らむ。Hub を常駐させない方向なので、残しても使わなくなる。

ドングルとのやり取りの書き方（Claude の判断）:

- **外部ライブラリを使わず、Windows の API（`hid.dll`、`setupapi.dll`、`kernel32.dll`）を P/Invoke で直接呼ぶ**。今の音声の切り替え（`src/AutoSwitch.Audio/ComInterop.cs`）と同じやり方で、依存を増やさない。
- （外した）HidSharp などのライブラリ: 楽だが、依存とライセンスの確認が増える。使う API は、列挙・開く・読む・書くの 4 つだけなので、自前で足りる。

## 設計

### 判定の規則

- 問い合わせの返答が来て、左右のどちらか 1 つ以上に残量（`0x00..0x64`）があれば **接続中（Connected）**。
- 問い合わせが 1000ms で時間切れになったら、新しい TID ですぐにもう 1 回だけ問い合わせる。2 回とも返らなければ **切断（Disconnected）**。
- 返答が来ても左右とも報告なし（`0xFF`、または `0x64` を超える値）なら **切断**（ケースが開いたまま両耳が入っている、などの場合。battery-hub の `headset is off` と同じ扱い）。
- 片耳だけ報告があれば接続中（アンチゴールのとおり）。
- 状態が変わったときだけ切り替える、という今の規則（`StateTransition.Resolve`）はそのまま使う。

### 問い合わせと返答の形

battery-hub の `inzone.js` と同じ。要点だけ書く。

- 対象: VID `0x054C`、PID `0x0EC2` の HID の collection のうち、Usage Page `0xFF04` / Usage `0x0001` のもの（COL03）。
- 問い合わせ（64 バイト、足りない分は 0）: `02 0C 01 00 FC 08 96 C3 41 04 01 <TID lo> <TID hi> <checksum>`。checksum は `[6..12]` の合計の下位 1 バイト。
- TID は 16 ビットの通し番号。問い合わせのたびに 1 増やし、`0xFFFF` の次は 1（0 は使わない）。最初は **`0x8000`**。Hub が使う小さな値（`0x01` など）からも、battery-hub の最初の値 `0x4000` からも離すため（battery-hub と同時に動くことがある）。
- 返答として受け付けるのは、`[0] == 0x02`、長さ 20 以上、`[9] == 0x04`、`[10] == 0x10`、`[11..12]` が送った TID、checksum（`[5..18]` の合計の下位 1 バイト）が `[19]` と一致するものだけ。`[14]` が左、`[16]` が右の残量。
- TID が重なって、Hub や battery-hub の返答を自分の返答と取り違えても、中身は同じ Buds のバッテリーなので判定は正しい。

### 知らせ（合図）の扱い

- 読み取り用のスレッドは、COL03 から届くフレームをずっと読み続ける。
- **type `0xA0`（`[10] == 0xA0`）のフレームが届いたら、監視ループの待機を起こす**（`WakeableWaiter.Wake`）。それ以外の中身は見ない（event の種類や左右のバイトは読まない）。Hub や battery-hub の問い合わせへの返答（type `0x10`）では起こさない。相手の問い合わせのたびにこちらも問い合わせて、問い合わせの頻度が相手につられて上がるのを避けるため（Claude の判断。builder check の指摘 3）。
- 自分の返答を待っている間に知らせが届いても、起こした印は残す（`WakeableWaiter` は待機の外で起こされた分を次の Wait まで持ち越すので、そのまま Wake を呼べばよい）。ふたを閉じた直後の知らせは、まだ返答が来る間に届くことがあるため、これを捨てると次の問い合わせが通常の間隔まで遅れる。
- 知らせで起こされた問い合わせの結果が接続中のままだったときは、**1 秒後にもう一度問い合わせる**（1 回だけ）。記録では、知らせが届いてから返答が止まるまで約 1 秒あったため。
- 起こされたときの最小間隔は、今の `WakeableWaiter` のもの（100ms）をそのまま使う。ふたを閉じた直後はフレームがまとまって届く（記録では 1 秒以内に 2〜20 個）が、待機が起こされた印は 1 回分にまとまる。

### 監視の流れ

- 監視ループ（`MonitorLoop`）の形は今のまま: 待つ → 起こされるか時間が来たら Tick → 待つ。
- Tick では、ドングルに問い合わせて状態を判定し、変わっていれば切り替える。
- 通常の問い合わせの間隔は `pollIntervalSeconds`（既定 **2 秒**。今の既定 1 秒から変える。知らせが来ればすぐ問い合わせるので、間隔は知らせが来なかったときの備えにすぎない。毎秒イヤホンに無線で問い合わせ続けるのは避ける）。
  - 作者の既存の `config.json` には `pollIntervalSeconds: 1` が書かれている可能性がある。その場合は 1 秒のまま動く（それでも問題はない）。
- ドングルが見つからない、開けない、書き込みや読み取りが失敗した（ドングルが抜けた、スリープからの復帰でハンドルが無効になった、など）:
  - 状態は変えず（切り替えない）、ハンドルを閉じて、`idlePollIntervalSeconds`（既定 5 秒）おきに探し直す。
  - 理由: ドングルが抜ければ Buds の音声デバイスも消えるので、Windows が既定のデバイスを自分で替える。こちらから切り替える必要はない。
  - ログは、見つからない状態になったとき・戻ったときに 1 回ずつ書く（5 秒おきに同じ行を書き続けない）。
  - **読めるようになったら、起動時と同じ扱いにする**（Claude の判断。builder check の指摘 2）: 今の状態を判定し、前の状態と同じでも、その状態に合わせて 1 回切り替える。抜いている間に Windows が既定のデバイスを替えているため、差だけで判断すると挿し直しても Buds に戻らない。`startupSyncMaxAgeMinutes: 0` のときは、起動時と同じく判定だけして切り替えない（起動時に見つからず後から見つかった場合も同じ）。
- スリープからの復帰（`ResumeGapSeconds` の判定）は今のまま残す。

### 起動時

- 今の起動時同期（ログの最後のイベントが新しければ切り替える）は廃止する。
- 代わりに、起動したら 1 回問い合わせて今の状態を判定し、**その状態に合わせて 1 回だけ切り替える**（Claude の判断）。今の起動時同期の目的（起動前に起きた接続・切断を反映する）を、より確かな形で満たす。
  - `startupSyncMaxAgeMinutes` を `0` にしていた場合（起動時同期を無効）の意味は、「起動時は状態を判定するだけで、切り替えない」に読み替える。
- ドングルが見つからなければ、状態は不明（トレイアイコンは枠だけ）のまま探し続ける。

### 設定

- `actionLogPath` は使わなくなる。`config.json` にあっても警告を出さずに無視する（作者の既存の `config.json` に書かれているため、毎回の起動で警告を出さない）。`AppSettings` からは消す。
- `pollIntervalSeconds`: 意味を「ドングルへの通常の問い合わせの間隔」に変える。範囲 1〜60 は今のまま。既定を 2 にする。
- `idlePollIntervalSeconds`: 意味を「ドングルが見つからないときに探し直す間隔」に変える。範囲・既定は今のまま。
- `startupSyncMaxAgeMinutes`: 0 なら起動時に切り替えない、1 以上なら切り替える、の真偽としてだけ使う。範囲・既定は今のまま（互換のため。値の大きさにはもう意味がない）。README にそう書く。
- 設定画面は、これらの項目を扱っていないので変わらない。

### 削除するもの

- `ActionLogReader`、`HubEventParser`、`SeenLogIdSet`、`LogChangeWatcher` と、それぞれのテスト。
- `IHubProcessProbe` / `SystemHubProcessProbe`（起動時同期の「Hub が起動しているか」の判定に使っていた）。
- 旧 PowerShell 版（`src/modules/` など）は残す（非ゴール）。

### 新しく作るもの（分け方は builder に任せる。目安）

- Core: 問い合わせのバイト列を作る、返答を照合して左右の残量を取り出す、の純粋な関数（TID と checksum を含む）。テストしやすいように、HID には触らない。
- Core: 「ドングルに問い合わせて、Connected / Disconnected / 読めない」を返すインターフェース（例: `IBudsProbe`）。`AutoSwitchEngine` はこれを受け取る。テストでは偽物に差し替える。
- 別プロジェクト（`AutoSwitch.Audio` と同じように、例: `AutoSwitch.Hid`）: P/Invoke で COL03 を探して開き、書く・読み続ける・知らせで起こす、を実装する。

## テスト

- Core の純粋な関数:
  - TID=1 の問い合わせが `02 0c 01 00 fc 08 96 c3 41 04 01 01 00 a0` のあと 0 で 64 バイトになる。
  - battery-hub の実測の返答 `021204ff0f0096c3140410010000630063ff60a7`（TID=1）から左 99 / 右 99。
  - TID が違う、event や type が違う、checksum が合わない、短いフレームは受け付けない。
  - 知らせのフレーム（上の例）は返答として受け付けない。
- 判定の規則: 左右とも残量あり → 接続、片方 → 接続、両方なし → 切断、1 回目の時間切れのあと 2 回目で返る → 接続、2 回とも時間切れ → 切断。
- `AutoSwitchEngine`: 偽の問い合わせで、状態が変わったときだけ切り替える、読めないときは状態を変えず idle 間隔にする、起動時に今の状態に合わせて 1 回切り替える（`startupSyncMaxAgeMinutes: 0` なら切り替えない）。
- 設定の読み込み: `actionLogPath` があっても警告が出ない。`pollIntervalSeconds` の既定が 2。
- P/Invoke の部分は、自動テストでは扱わない（実機で確かめる）。

## 実機での確認（実装のあと、インストールして）

Hub を終了した状態で:

1. Buds を取り出すと、1〜2 秒で Buds に切り替わる。ふたを閉じると、3 秒程度（遅くとも 5 秒）でスピーカーに切り替わる。
2. 片耳だけケースに戻す（ふたは開けたまま）と、切り替わらない。
3. 両耳をケースに戻してふたを開けたままにしたとき、ログに何が出るかを記録する（返答が左右とも報告なしになるのか、返らなくなるのかは確かめていない）。
4. Buds を着けたままアプリを起動すると、Buds に切り替わる。ふたを閉じたまま起動すると、スピーカーに切り替わる。
5. ドングルを抜くと、ログに 1 回だけ「見つからない」が出て、切り替えは行わない。挿し直すと戻り、今の状態に合わせて動く。
6. PC をスリープして復帰したあとも、1 が成り立つ。

Hub を起動した状態で:

7. 1 と 2 が成り立ち、Hub の表示（接続状態、バッテリー）がおかしくならない。
8. battery-hub も同時に動かして、1 が成り立ち、battery-hub の表示もおかしくならない。
